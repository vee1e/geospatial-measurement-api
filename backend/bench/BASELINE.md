## Where the time goes

Profiled `process_file` on the 10,000-feature file took 1.013 s. The three biggest cost centres:

1. **Measuring and reprojecting every feature**, `app/geo/measure.py:47` - 0.576 s cumulative (57% of the run), 58 us per feature. Inside it, `app/geo/crs.py:142` (`Projector.project`) accounts for 0.334 s: shapely `ops.transform` walks every coordinate through pyproj.
2. **Parsing the KML**, `app/geo/readers.py:297` - 0.315 s cumulative (31%), covering `ElementTree.parse` (0.085 s), coordinate parsing and property extraction (`app/geo/readers.py:277` 0.096 s).
3. **Assembling the response document**, `app/pipeline.py:123` (`_build_payload`) minus the two above: about 0.099 s for `_layer_bounds`, `_summarise` and the per-feature list comprehension that becomes the 3,029,802-byte JSON document. Storing it (`app/pipeline.py:96` `db.save_measurements`) plus the status updates cost the remaining 0.023 s.

Read once against the scaling table: no part of the pipeline grows faster than the feature count. Per-feature cost falls from 0.121 ms at 100 features to 0.058 ms at 10,000 because the fixed per-file cost (CRS resolution, import-time work already paid, one document write) is spread over more features. Memory grows linearly: 53.2 MB of growth for 10,000 features, roughly 5.3 KB per feature, over a 52.3 MB interpreter baseline.

Concurrency does not help: the worker is one thread, so 8 simultaneous uploads take 0.55 s wall against 0.53 s serially, and each upload request waits 18 ms instead of 2 ms because the event loop and the worker compete for the GIL.

Not measured here: RSS of the serving uvicorn process itself while requests run [not measured], disk write cost of the upload separated from network [not measured], and any allocation inside C extensions (shapely, pyproj, libexpat) which tracemalloc cannot see [not measured].
